# Auditoria integral de YenHubs - Julio 2026

Fecha de corte: 13 de julio de 2026.

Estado: auditoria tecnica en curso. El analisis local y las primeras correcciones estan completados; la validacion
visual, multiusuario y de infraestructura necesita que DigitalOcean vuelva a estar operativo.

## 1. Conclusion ejecutiva

YenHubs es recuperable y las personalizaciones principales siguen compilando. No conviene actualizar todo antes de
restaurar: primero hay que levantar el estado congelado, comprobar los flujos reales y despues actualizar cliente e
infraestructura en ramas distintas.

La version congelada no debe considerarse lista para uso publico prolongado sin remediar Reticulum. El backend usa una
base Elixir/Phoenix antigua con vulnerabilidades de denegacion de servicio, XSS y SSRF. Hubs CE 2.1.0 conserva esas
mismas versiones, por lo que actualizar solo el generador no resuelve el problema.

Los bots tienen ahora un contrato de privacidad razonable para un MVP:

- la clave OpenAI solo existe en backend;
- las peticiones usan `store: false`;
- no se guarda historial en Reticulum ni en el orquestador;
- el historial del navegador vive en memoria y se pierde al abandonar la sala;
- entrada y salida pasan por moderacion;
- hay limites de longitud, frecuencia y acciones;
- OpenAI recibe un `safety_identifier` seudonimo, no el identificador de cuenta en claro.

Esto reduce datos propios almacenados, pero no equivale a Zero Data Retention en OpenAI. Para un evento con publico se
necesita aviso de privacidad y, si se exige retencion cero del proveedor, solicitar ZDR a OpenAI.

- Mensajes y errores de chat bot en espanol sin exponer errores internos.
- El cliente envia solo nombres `spawbot-*` saneados como contexto.
- La accion de navegacion ya no se emite desde el navegador.
- Validacion GLB 2.0, limite 64 MiB, limpieza de object URLs y recuperacion de errores.
- Correccion de tercera persona al entrar en VR.
- Reserva de asientos bitECS: respeta `Can be occupied` y recorre candidatos hasta encontrar uno libre.
- Correccion del desbordamiento de notificaciones en pantallas estrechas.
- Workflows reutilizables fijados por commit.

- `npm run build`: correcto, con warnings de tamano.
- El locale `es.json` contiene todas las claves del locale base `en.json`; los identificadores dinamicos requieren
  comprobacion visual porque no todos son claves directas.

### Bot orchestrator

- Autenticacion interna fail-closed con clave minima de 32 caracteres y comparacion constante.
- Express sin cabecera identificativa y body JSON limitado.
- Moderacion de entrada y salida con `omni-moderation-latest`.
- Responses API con `store:false`, salida corta y reasoning bajo.
- Rate limit por sala, bot y usuario.
- Fallback sin repetir el texto privado del usuario.
- Reconciliacion de salas y parada de runners obsoletos.
- Backend por defecto `ghost`; Chromium limitado a una sala si se activa.
- `phoenix-js` fijado a commit.

Validacion local:

- 7 pruebas automatizadas: correctas.
- `npm audit --omit=dev`: 0 vulnerabilidades.
- `node --check app.js` y `node --check run-ghost-runner.js`: correctos.

### Reticulum

- Configuracion de bots normalizada en 0..10 y prompt limitado.
- Endpoints internos fail-closed y comparacion constante.
- El identificador de cuenta solo viaja por la red interna y se seudonimiza antes de OpenAI.
- Acciones de bot validadas y emitidas por backend.
- Clave de bot minima de 32 caracteres tambien en el canal Phoenix.
- Se elimino un PAT hardcoded del build de Spoke.
- `mix format --check-formatted` sobre los archivos modificados: correcto. La comprobacion global sigue fallando en
  archivos heredados no tocados; no se hizo un reformateo masivo durante la auditoria.

Limitacion de validacion: el proyecto fija Elixir 1.14.3/OTP 23, mientras la maquina tiene OTP 29. La compilacion local
falla en dependencias antiguas (`ssl_verify_fun`), no en el codigo auditado. La modernizacion debe incluir CI/container
con toolchain reproducible; no se debe forzar el lock actual sobre OTP 29.

### Generador Hubs CE

- Las configuraciones de cert-manager, redireccion SSL, clase de ingress y permisos HAProxy estan en el template.
- Se elimino la generacion del secreto autofirmado `cert-hcce`, que no tenia consumidor.
- El generador devuelve codigo distinto de cero si falla; ya no puede aparentar exito tras una excepcion.
- `npm run gen-hcce` valida el manifiesto y exige exactamente un `Service` de tipo `LoadBalancer`.
- Se elimino `node-forge` y se fijo `tmp` a una version corregida; `npm audit` del generador devuelve 0 avisos.
- El manifiesto generado se aplica sin modificaciones manuales. Una incidencia se corrige en el template y se regenera.

## 5. Privacidad y guardarrailes de bots

### Datos que procesa el backend

- `hub_sid`, `bot_id`, mensaje limitado a 800 caracteres y lista saneada de hasta 64 waypoints.
- Prompt de sala limitado a 1500 caracteres.
- Identificador de cuenta solo para rate limit y derivacion HMAC.

### Datos que no se almacenan en YenHubs

- No hay tabla ni fichero de conversaciones.
- El orquestador no escribe prompts ni respuestas en logs.
- El cliente no usa `localStorage` para historial del bot.
- Al cambiar o salir de sala, el estado React de conversaciones se elimina.

### Limite externo

`store:false` impide conservar estado de Responses para recuperacion por API. Aun puede existir retencion de monitoreo
de abuso de OpenAI durante hasta 30 dias salvo que la organizacion tenga Zero Data Retention aprobada. Antes de publico:

1. publicar aviso corto de privacidad;
2. no pedir ni incentivar datos sensibles;
3. fijar prompt y politica de moderacion del evento;
4. decidir si hace falta solicitar ZDR;
5. probar el modelo en espanol con casos de abuso y prompt injection.

## 6. Auditoria funcional pendiente en vivo

La siguiente matriz necesita el cluster:

- Home, login por email, crear sala, entrar como lobby y como participante.
- Audio/WebRTC entre dos navegadores y salida/reentrada.
- Spoke: cargar, editar, publicar y volver a abrir escena.
- Third person en desktop y retorno forzado a primera persona en VR.
- Sit/Stand con dos usuarios y asientos ocupables.
- Subida de avatar normal, RPM y Avaturn privado; preview, featured y seleccion.
- Bots ghost: 1, 5 y 10 bots; late join, reconexion, desactivar/reactivar sala y cinco salas.
- Chat IA: moderacion, rate limit, prompt injection, accion de waypoint e historial solo de sesion.
- Capturas 1440x900, 1024x1366 y 390x844 para home, lobby, sala, toolbar, sidebars, chat y avatares.

## 7. Criterio de salida

No marcar la auditoria como cerrada hasta que:

1. todos los P0 esten corregidos o exista una aceptacion de riesgo escrita y temporal;
2. el baseline se restaure desde backup y pase smoke tests;
3. las imagenes activas queden registradas por digest;
4. exista rollback probado de imagen y base de datos;
5. el flujo IA tenga aviso de privacidad y pruebas de guardarrailes;
6. la auditoria visual tenga capturas comparables y lista de correcciones verificada.
